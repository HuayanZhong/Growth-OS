# Agent Note: 操作审计日志（阶段三 3.4）

Status: implemented

## Problem

服务端写操作（会话 CRUD/fork 等）缺少"谁在何时对什么做了什么"的记录。审计必须复用既有机制（append-only 事件存储模式 + 响应信封），且不能把审计硬塞进会话事件流——审计操作是跨域的，没有 sessionId。

## Decision

- 独立 `audit` 域（`modules/audit/`）：`audit_logs` 表 append-only（seq 插入序 + id unique），列结构为 actorId/action/resourceType/resourceId/timestamp/details，不复用 `session_events` 表——审计无 sessionId，塞进会话事件流会污染其契约。
- 域间走 service 注入：各域 service 注入 `AuditService`，在**写操作成功后**显式 `record()`。动作集已覆盖 `session / agent / skill / project` 四域的 create/update/delete（外加 session.fork）；files 域随存储适配器落地按同模式接入。
- actorId 来自 JWT `sub`（controller 经 `@CurrentUser` 传入 service）——审计主体恒为登录用户，桌面单租户场景够用。
- **审计失败向上传播**（不吞错）：审计完整性优先于操作可用性。删除会话的审计在删除事务内记录，事务回滚则审计一并回滚——被删资源的标题等上下文只存在于事务内。
- 查询端点 `GET /audit-logs`（JWT 保护，倒序 + actor/action/resource/时间窗过滤 + limit）；记录无对外 POST 端点，审计只由服务端产生。

## Alternatives considered

- 审计写进 `session_events`：被否。sessionId 必填的会话事件流装不下跨域操作，且管理操作混入消息级事件会污染回放/投影。
- NestJS 拦截器/装饰器 AOP 自动审计：对写方法做隐式拦截看似省事，但审计细节（details 摘要、resourceId 语义）是每个操作的业务知识，集中到装饰器元数据里反而更难维护；显式调用与架构约定（域间 service 注入）一致。
- 审计失败吞错 + 告警日志：单用户桌面应用没有独立的告警通道，吞错等于静默丢审计；fail fast 与项目不变量立场一致。

## Consequences

- `@growth-os/types` 新增 `AuditLog`/`AuditLogQuery`/`AuditApiMap` 契约；`GET /audit-logs` 自动受全局 JwtGuard 保护。
- 审计 UI（计划 P2 项）与更多域的写操作审计随各域 CRUD 落地扩展；真实库冒烟验证过 create/fork/update/delete → 过滤查询 → limit 全链路，冒烟脚本已删。
